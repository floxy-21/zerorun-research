# Prospective feasibility protocol, 29 October 2026

This is exploratory development, not confirmation. The selected research object is the cost and qualification boundary of **historical successful-status reuse**. No algorithmic priority, general deterministic execution, or natural agent-workflow speedup is claimed. The intended paper compares complete deployment costs and identifies the maximum unmeasured human-review cost a deployment could tolerate.

The two pilot projects are cachetools and Blinker. The original rule's `pallets/blinker` returned 404; the canonical repository is `pallets-eco/blinker` (GitHub repository ID 11147893). This corrects the owner of the same selected project, without replacing a workload. Its 60-run sample contains only one test-workflow request; that small denominator will be retained. Cachetools contributes the most recent 20 CI requests within the original cutoff. Outcomes were not used to select requests. These requests are standardized source replays, not reconstructions of their original CI environments or evidence that users wanted historical answers.

For initial executable calibration, use the most recent selected source from each pilot, two complete three-arm blocks, and one producer plus four unchanged status consumers per arm. The repeat requests are constructed handoffs. All six arm orderings will be used twice in the planned main study (12 blocks per supported target, two separate jobs); two pilot orders establish feasibility only. Main candidates remain those in COHORT_RULE.json, with all selected cases retained, including failures. Main execution cannot begin until the implementation, exact input snapshots, qualification decisions, correctness cases and analysis are frozen in the experiment pack.

The three arms are ordinary fresh full-tree execution, the released ZeroRun 0.5.3 MCP service plus the external exact-state qualification gate, and a separately implemented small authenticated receipt cache plus that same gate. Both reuse arms return historical success, never current diagnostics or artifacts. The receipt implementation must inspect the pinned runtime, bind complete input bytes/modes plus command/environment, authenticate the receipt with an external private key, validate input identity before and after lookup/execution, stage a private execution copy on a miss, and decline to cache failures. It does not import ZeroRun's identity, cache, or execution code. Fresh and receipt arms use the same resource/network/read-only policy and one JSON-RPC subprocess per request. The fresh arm needs no reuse qualification. The actual ZeroRun source remains unchanged.

Execution normalization is material: ZeroRun normalizes staged file/directory timestamps to zero. The receipt miss does the same, and both bind root directory mode. Ordinary fresh execution sees the original full-tree metadata. We therefore require the intended full-tree and staged task's nonempty node outcomes to agree for each fixed source before timing; this is observed exact-target equivalence, not proof for arbitrary future programs. A metadata-dependent counterexample is a qualification failure and must remain visible. Fresh-only is not charged unnecessary staging. The reference service's `verify` option means bypass and obtain fresh diagnostics; it is not advertised as ZeroRun's cache-comparison/invalidation operation.

Measure complete outer request time, arm-specific initialization, source acquisition/materialization, environment creation and qualification automation separately. Exclude research-only oracles from operational cost and disclose them. Record assistant-operated review intervals and action records prospectively; do not reconstruct missing earlier time or equate model elapsed time with human labor. Unknown human review remains a sensitivity variable. Common costs are charged equally in first-use scenarios. Cache misses, refused qualification, failed tests, setup errors and cleanup all retain terminal dispositions and incurred time.

Before timing any selected target, compare full-tree fresh and staged execution using an independent pytest outcome capture (nonempty node collection, per-phase outcomes, exit status). Match historical receipt status to the independently fresh outcome. A designed boundary matrix will separately test changes, restoration, unqualified edits, receipt corruption, failure, omitted inputs, runtime/environment changes, and fresh-output requests; zero observed mismatches is not a population safety probability. Quiescent owned checkouts and a trusted host/operator are assumptions; repeated scans do not prove atomicity under arbitrary mutation.

Primary main endpoint: per-target paired complete-chain time difference at one consumer; secondary prefixes zero, two and four. Resample whole paired blocks for 95% percentile intervals with 10,000 draws and fixed seed 20261029. Report raw blocks and per-target results; do not pool nodes or consumers as independent observations. Report both comparator differences, without significance tests or acceptance probabilities. A practical superiority statement requires the entire interval to exceed 5% of fresh mean time and all correctness checks to pass. Otherwise the result is mixed, slower or uncertain. Negative results are valid outcomes of this experiment.

The conditional human-review budget is the measured fresh-chain cost minus all measured reuse-chain and additional automation costs, expressed first in seconds of serialized elapsed time. Human monetary/active-effort conversions require explicit rates and are separate sensitivity scenarios. Break-even denominators at or below zero remain undefined, rather than being clamped. Refit or changed protocols after pilot are recorded before main execution. A false success stops the affected comparison and triggers repair with the failed attempt retained.
