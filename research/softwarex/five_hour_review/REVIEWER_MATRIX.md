# Reviewer-facing evidence decisions

This matrix distinguishes testable software claims from wider inferences. It
does not convert successful demonstrations into an acceptance probability.

| Reviewer question | Evidence that can answer it | What remains outside that evidence |
| --- | --- | --- |
| Can a new operator install and invoke the current release? | Fresh external installation of the exact 0.5.2 wheel; all 36 installed module hashes; CLI help and current public regression suite; existing public-guide reproduction explicitly labeled 0.5.1. | Independent human installation success, broad OS coverage and production support. |
| Is the new MCP change a real usability improvement rather than a new engine? | Exact two-module versioned diff; AST/catalog proof that executable behavior and argument schema stay the same; tests that discovery exposes supported parameters, status meaning, output limits and authorization requirements. | Causal improvement in arbitrary models' comprehension without a prospective paired model experiment. |
| Does reuse help on issue-derived code? | Fixed outcome-independent selected cases; paired complete cold-producer-plus-consumer clocks; separate setup/diagnostic/oracle clocks; case-level dispositions and exact repository/patch identities. | Natural repeated-state prevalence, live-agent end-to-end acceleration or universal cache eligibility. |
| Does the client distinguish prior status from new diagnostic output? | Actual raw client calls and interpretations of clearly identified tool results, assessed against a frozen rubric; failures retained. | Population accuracy or independent developer adoption. |
| Is the result safe to reuse in the recorded workload? | Exact frozen source/runtime bindings and a separate fresh oracle with full node outcomes for each reported completed state; explicit refusals and mismatches. | A proof of arbitrary task determinism, zero future safety failures or permission to authorize production repositories. |
| Why does the software exist beside other caches? | Operator-qualified whole-task identity, explicit prior-success status without pretending to return fresh stdout/stderr, a separate fresh diagnostic path and an inspectable AI-client interface. | Inventing hashing/caching, being the first AI cache, or superiority to systems not fairly evaluated. |

## Three protocol pitfalls to avoid

1. **Selecting the successful workload after observing benefit.** Retain the
   prespecified acquisition order, disjoint pilot and selected failures. A new
   supported-environment protocol may be justified by compatibility findings,
   but it is a new version and the unsuccessful original remains visible.
2. **Comparing a warm consumer with an uncharged seed.** The primary controlled
   comparison includes the cold producer and consumer in both arms. Report
   consumer-only savings only as conditional latency, never complete-workflow
   savings. State whether setup is common or arm-specific, and exclude independent
   research oracles symmetrically from the treatment while reporting their cost.
3. **Calling every case an AI task or every reconciliation a safety guarantee.**
   Reference-patch handoffs, genuine fresh-only agent sessions and model
   interpretation turns are different denominators. Exact execution evidence
   is a software application result, not prevalence, user research or an
   exhaustive guarantee. Any completion flag not independently recomputed must
   be described as producer-reported, alongside the raw records that were checked.

For SoftwareX, the highest-value improvement is a useful, reproducible
application with honest scope and a low-friction installation path. Increasing
test counts, adding a DOI or polishing the narrative cannot substitute for that
application. A DOI/CITATION file can improve citation and persistence without
creating novelty or validating performance.
