# Image-contained dependency deployment, prospective version 2

Freeze this protocol, builder, runner, exact data ledger and image receipt before
the corresponding experiment. This is a separate deployment representation of
the existing supported result-only interface, not a new algorithm, relaxed
eligibility rule, replacement of version 1, or a natural autonomous-task study.
The decision to investigate image-contained dependencies was made before either
new handoff pilot/main result, from the earlier descriptive fingerprint costs.
No performance outcome determines case inclusion. All 30 main candidates and
the two disjoint pilot cases come from the unchanged acquisition ledger. No
additional handoffs or repeated consumers are introduced to improve results.

## Single deployment difference

Version 1 puts the exact hash-locked pytest/pretend closure in each source
workspace. Version 2 copies the same dependency files into system site-packages
of an image derived from the same pinned CPython 3.12.14 base. The image identity
then covers those immutable dependencies; project source still receives the
unchanged complete input scans. The task command becomes `python -m pytest`,
with the same cacheprovider setting and issue targets. No local dependency
directory is omitted while still being used. Image file locations and import
paths differ, so fresh-oracle agreement is measured rather than assumed.

The ZeroRun runtime remains the exact original 36-file 0.5.1 public runtime.
Runtime inspection, RepoDigests checks, source fingerprints, cache provenance,
staging, result semantics and authority code are never patched. The only
runtime parameter substitution remains the symmetric 120-second execution cap
declared in v1. A research wrapper explicitly substitutes image-contained
workspace preparation and a previously built image for v1's dependency-layer
materialization. It retains the exact v1 case, operation, oracle and aggregation
code. These research-adapter substitutions are frozen and recorded separately;
they are not described as an identical experiment to v1.

## Legitimate immutable image preparation

Use the existing hash-locked helper to acquire/freeze pytest and pretend from
their recorded wheel hashes. Preserve its provenance and a complete byte/mode
inventory. The Docker context contains only those files, the exact dependency
lock, and the new Dockerfile. Build FROM the pinned public base with build
network disabled and without package installation during Docker build.

A new task-owned registry may listen only on 127.0.0.1, with an exact pinned
official registry image, an isolated store and a recorded container ID. Push
and pull the derived image normally, obtain its real registry digest, and
require the existing ZeroRun runtime inspection to accept it. Never substitute
an image configuration ID for a registry manifest digest, invent RepoDigests,
modify Docker's daemon configuration, change host trust, or expose the registry
on a public interface. Stop only the exact task-owned registry container after
image preparation; retain its store for archived reproduction. No external
registry credentials, payment or global configuration changes are required.

Record base/derived/registry image IDs, RepoDigests, Dockerfile, dependency-file
hashes, build commands, all subprocess results and setup time. A local registry
digest is not a publicly downloadable artifact. Publish the recipe and hashes,
and disclose any absence of an independently accessible exact image. Recipe
rebuilds may yield another digest; no bit-identical rebuild claim is made unless
verified. Reproducers must pin and record the image they actually built.

## Fixed comparison, denominators and interpretation

Within the new deployment, use the exact v1 cold producer-plus-one-consumer
comparison, two counterbalanced paired blocks, separate fresh-diagnostics call,
and independent fresh oracles. Both fresh and ZeroRun arms run the same derived
image and source. Preserve every candidate disposition, partial operation,
negative timing result, unsupported environment and correctness stop.

Report producer-plus-consumer costs, consumer waiting, per-arm source preparation
and image preparation separately. Do not charge image preparation only to the
fresh baseline, or hide the cost of distributing a custom image. Cross-deployment
differences between v1 and v2 are descriptive: run order and changed import/file
location prevent a clean causal claim about fingerprinting alone. This study
does not measure natural repetition frequency, AI task completion, adoption,
CPU/energy savings, commercial demand or acceptance probability.

The outer v2 receipt preserves actual before/after runtime and wrapper source
inventories; inner v1 records retain the operation-level evidence. Read-only
reconciliation must validate both layers and image provenance, not trust a final
pass flag. A negative full-chain result remains a valid observation.
