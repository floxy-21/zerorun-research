# Controlled public-issue-state handoff, version 1

This is new evidence, not a relabeling of the previous synthetic model trials.
The sampling ledger must be frozen before execution. The acquisition ledger
records all selected candidates, including unavailable ones. The target is 30
public issue-derived cases from ten repositories (three each), not 30 AI tasks.
Two separate pilot cases are excluded from the main analysis. Repository choice
is a disclosed convenience restriction to the existing Python/pytest laboratory;
neither selection nor replacement may depend on observed ZeroRun speed or hits.
An incomplete candidate pool or campaign remains incomplete. No replacement
repositories/cases are introduced after execution to obtain favorable results.

## States and scope

Each case binds its exact benchmark metadata response, public base-commit source
archive, reference patch, test patch, reviewed pytest file targets and licenses.
Reference patches construct a repaired issue state; they are not agent edits.
Only ordinary bounded archive members and literal reviewed patch paths are
accepted. Recorded benchmark installation/test shell strings are never executed.
Targets are frozen before timing. Missing dependencies, unsupported patches,
baseline failure, no collection, setup refusal and timeouts remain dispositions.
No new upstream dependency is guessed or installed after seeing an outcome.

The existing digest-pinned CPython 3.12.14 image and hash-locked pytest/pretend
environment are reused. This is a controlled compatibility environment, not a
claim to reproduce each benchmark's original environment or solve its issue.
Execution is through the trusted-operator API, never MCP; no MCP authority is
created. A private authentication root is generated solely for laboratory cache
records and must not be published. Whole-source inputs include every ordinary
source member and the frozen dependency environment; no input is omitted to
increase reuse. Execution is read-only, network-disabled and resource bounded.

## Fixed comparison

Each executable case has two cold paired blocks. In block one, arm order is
selected by SHA256 of the fixed seed and case ID; block two reverses that order.
Every arm has a separate, byte-equivalent source/environment copy and the
ZeroRun arm starts with an empty cache. No performance warmup is discarded.

* Fresh chain: one producer validation followed by exactly one unchanged-state
  downstream fresh status validation using the independent plain Docker runner.
* ZeroRun chain: one cold producer invocation followed by exactly one unchanged
  downstream status request. A hit is observed, not manufactured or asserted.
* Fresh-diagnostics check: after the status chain, one ZeroRun fresh verification
  on that state. Report its cost separately; never count it as reuse or include
  it only in the fresh baseline. It tests the documented fresh-request route.
* A separate instrumented fresh oracle follows each arm's status chain. Compare
  collected node identities/outcomes across arms and with the product exit
  status. The oracle is outside the two timed chains and does not seed or alter
  their cache. Its cost and invocations are retained as research instrumentation.

Primary costs include both producer and consumer complete outer invocation
times, including cold cache creation, fingerprints, snapshots, lookup and test
execution. Report downstream waiting separately. Record common dependency build
and per-arm materialization/setup separately; also report setup-inclusive costs.
Do not add inclusive internal timing aggregates to outer clocks. Do not infer
CPU, energy, monetary, token or autonomous workflow savings from wall time.

The deliberately unchanged handoff creates an opportunity; it does not measure
the prevalence of opportunities in natural coding. One seed and one consumer
has at most a 50% hit fraction. The earlier 54--64% short-subject break-even
figures make negative full-chain outcomes plausible. A 25--30% saving is not an
eligibility rule, stopping gate or assertion. No extra consumers are introduced.

## Correctness, failures and stopping

Before timing, require a complete, nonempty passing fresh oracle on the repaired
state. This is compatibility screening, whose time and outcome are retained.
Unsuccessful candidates remain in the original denominator, not replaced.
After every chain, require unchanged source/environment identity and complete
fresh oracle agreement. A success-versus-fresh-failure discrepancy, source drift
or cache identity inconsistency stops the campaign as a material correctness
failure; preserve every file already written. A failed baseline, unsupported
case or infrastructure timeout stops that case, not an unrelated completed case.
No automatic retries until pass. The two blocks are repeated measurements of a
case, not independent issues. All assigned cases, all attempted blocks and all
operation outcomes are reported, including missing/unexecuted stages.

The source, protocol, data ledger, runtime files and helper bytes are frozen in
the receipt before any test. Durable per-operation records survive failures.
The run budget is fixed by explicit campaign deadline and recorded symmetric
per-execution timeout. Deadline-excluded cases remain `NOT_RUN_BUDGET`. No
partially observed cost is assigned zero or treated as a completed speed ratio.
No model calls are made by this runner. Separately recorded model demonstrations
must have their own protocol, denominator, authority and results.

## Reproduction and interpretation

The runner accepts a fully bound local selection ledger and makes no network
requests for case data. Source acquisition is a separate auditable stage.
It uses only the frozen public runtime and helper, not private working changes.
The read-only validator recomputes observations and summaries from retained raw
records; the full local workspaces/private cache are not publication evidence.
A credible result may be a useful consumer-latency benefit with negative total
cost. Preserve that distinction and do not convert results into acceptance odds.
